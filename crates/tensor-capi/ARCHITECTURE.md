# edgefirst-tensor-capi — Architecture

The C API for `edgefirst-tensor`. A sibling crate, mirroring the `python-*` layout, so `extern "C"` stays out of the Rust crate and the `cdylib` can be built without a Rust consumer ever compiling the FFI layer.

Ships as **`libedgefirst_tensor`** with one header, `edgefirst/tensor.h`. The `-capi` suffix names the source crate only and never reaches a filename a consumer links against — a test asserts this, because cargo does not remove artifacts when `[lib] name` changes and a stale `libedgefirst_tensor_capi.*` could otherwise be installed.

## The problem this crate solves

Rust has no stable ABI. Every `cdylib` statically links its own copy of its Rust dependencies, so a library **cannot dereference a `TensorDyn` created by another copy of the code**. An earlier design kept every accessor `static inline` in the header, so no library ever exported `ef_tensor_shape` and there was nothing for the dynamic linker to interpose — the class of failure recorded in the mobile-sdk repo as an iPhone NULL jump.

The current design dissolves the hazard instead of defending against it: `libedgefirst_tensor` is the **one implementation home** for the tensor type, the only library that exports `ef_tensor_ndim` and friends, so there is nothing left for a second exporter to collide with. Every sibling `-capi` crate (`image`, `codec`, `decoder`, `tracker`) links this library dynamically rather than embedding a private copy. The rest of this document describes that contract as it stands today; a retrospective on how the crate got here — a transition dispatch mechanism this document used to describe as current — is in its own section below, clearly marked as history rather than left mixed into the present-tense description.

## Three surfaces, and layout appears in exactly one

| Surface | Scope | Mechanism |
|---|---|---|
| Opaque handle | in-process | exported accessor functions of `libedgefirst_tensor`; nothing else declares layout |
| Builder | construction | sticky errors, per-field validation |
| `(blob, handles)` | cross-process | handles travel out of band and are referenced **by index** |

### The exported accessors, and the opaque handle

The read accessors — `ef_tensor_ndim`, `ef_tensor_shape`, `ef_tensor_strides`, `ef_tensor_dtype`, `ef_tensor_storage_kind`, `ef_tensor_plane_count`, `ef_tensor_format`, `ef_tensor_colorimetry`, `ef_tensor_plane_at`, `ef_tensor_view_origin` — are ordinary `#[no_mangle] extern "C"` functions in `src/handle.rs`, exported by this library alone (the builder, mutators, quantization accessors, `map`/`unmap`, and serialization round out the rest of the exported surface, in their own source files below). There is exactly one exporter of any of them, so there is nothing for the dynamic linker to interpose.

`ef_tensor` is fully opaque in the public header: no vtable, no struct body, no `static inline` bodies. `edgefirst/tensor.h` declares the accessors and says nothing about how a tensor is laid out in memory. cbindgen regenerates the header on every build (`build.rs`, keyed off `src/` and `cbindgen.toml`) and its output is byte-stable — a lesson from an earlier round of this series: cbindgen cannot emit the accessors from a `macro_rules!` body without the generated signatures drifting between runs, so they are written as explicit `extern "C"` functions.

Every sibling library besides this one exports essentially one real symbol family of its own, its **constructors** (`ef_image_processor_create_image` and so on) — never tensor accessors, which live only here. That is correct: "who allocated this" is the one question where library identity still matters for a *constructor*. It is no longer true for anything else, including destruction — see the free-routing section below.

### Layout crosses only through `tensor-abi`; the contract with `tensor-ffi`

`crates/tensor-abi` is the single declaration home for the plain values that do cross the boundary — `EfTensorPlane` and the `EfDtype`/`EfStorageKind` vocabularies. It has zero dependencies and must never gain one, so every sibling `-capi` crate imports this one definition instead of carrying an "identical copy". `tensor-capi/src/codes.rs` keeps the exhaustive compile-time const-assert block that checks every enumerator against `edgefirst-tensor`'s Rust vocabulary at build time — the authority check this repo added after Python's `MEM == 3` collided with C's `PBO == 3`. (`EfDetectBox` and `EfDetectBoxList` are unrelated to this crate: both are declared in `edgefirst-decoder-capi`, their one implementation home.)

`crates/tensor-ffi` is the other side of a two-sided contract: declarations-only `extern "C"` bindings to every function this library exports, with no `#[link]` attribute of its own — linking is left to the consumer. **The exact count is not repeated here** — a hardcoded number rots exactly as this document's own "38" once did, back when the real count had already moved to 56. `tensor-capi/tests/check_abi.rs` is the source of truth instead: `every_ffi_declaration_is_a_real_export` and `every_exported_ef_symbol_is_declared` check that `tensor-ffi`'s declarations and the built library's real exports are exactly the same set (DECLARED ⊆ `nm -gU` output, and the reverse), and `the_ffi_declaration_count_matches_the_header` cross-checks that count against the generated header's own declaration count — so a declaration without a matching export, a load-time failure waiting in every consumer, is caught here instead of restated as a number that can silently go stale.

The symbol table is trimmed to match: a Linux version script and a macOS exported-symbols list export only `ef_*`, with the soname carrying the major version on Linux and `@rpath` install name on macOS.

### Why a wrong-library free can't happen — a guarantee that changed shape, not just its enforcement

**History, not the current design:** earlier revisions of this crate solved cross-library dispatch with a per-object vtable. Each `EfTensor`'s first member pointed at a table of function pointers, and `ef_tensor_free`, along with every accessor, called through it rather than assuming its own layout — because until every sibling minted through this one library, a handle from `ef_image_processor_create_image()` might carry a table pointing back into `libedgefirst-image`'s own, separately-compiled copy of the implementation. Freeing through the wrong copy would have been silent heap corruption, not a crash, and the vtable's job was to make that impossible during the interregnum. A parallel guard sat on `ef_tensor_retain`/`_map`/`_unmap`/`_copy_to`: each checked that the handle carried *this* library's own vtable and returned `ENOTSUP` for a foreign one, so the map model and the refcount could be built and tested on own-minted tensors only, without waiting for every sibling to switch.

**That is gone, not merely hidden.** Every sibling `-capi` library now links this crate's `libedgefirst_tensor.so` dynamically instead of embedding a private copy, so **there is exactly one implementation of `ef_tensor_free` — and of every accessor — in the whole process.** `EfTensorImpl` has no `vt` field; `ef_tensor_free` unconditionally calls the one `release_own`; `ef_tensor_retain`/`_map`/`_unmap`/`_copy_to` accept any handle regardless of which library minted it, because there is no second implementation left to distinguish it from.

The interesting part is not merely that the guard was deleted — it is that the *guarantee itself* moved from **tested** to **structurally unrepresentable**, which is worth spelling out because it is the clearest example of that move anywhere in this codebase. Before, correctness meant a runtime counter proving one specific call happened to land in the right place: real evidence, but evidence about *one execution*, and a bug in a path the counter's own test did not happen to exercise could still exist. Now, `image-capi`'s `the_two_libraries_export_no_symbol_in_common` test (and the equivalent shape in every other sibling) asserts that no sibling `.so` exports any `ef_tensor_*` symbol at all — proving, at the symbol table, that there is no second implementation for a free to ever be misrouted to, **even in principle**. A test that watches one call route correctly can miss a bug on a call it never made; a test that proves no alternative destination exists has nothing left to miss.

### The builder

Errors are sticky: after a setter fails, later setters no-op — returning the pending error *without running* — and the terminal call reports the **first** failure. This is what lets a caller chain and check once. Reporting the most recent status instead would name whichever call happened to follow the real fault, and letting later setters take effect would let a terminal call build from a half-populated builder that looks valid.

`alloc` takes no planes and derives storage; `wrap` requires at least one plane and adopts its handles. Misuse of either is a per-field error, not a documented convention. Neither consumes the builder — `alloc` in a loop fills a V4L2 pool.

### Vocabulary enums

`ef_dtype` and `ef_storage_kind` are named enumerators, but the setters take `uint32_t`. That is deliberate: transmuting an out-of-range value from C into a Rust enum is undefined behaviour, whereas validating an integer is not. Every enumerator's value is asserted against the Rust vocabulary **at compile time**, so a renumbering on either side is a build failure rather than a silent misinterpretation — the failure mode this repo already hit when Python's `MEM == 3` collided with C's `PBO == 3`.

## Map window and refcounts

Five entry points make up the whole CPU-access and lifetime story for a handle from C: `ef_tensor_retain` (`handle.rs`), `ef_tensor_map` / `ef_tensor_unmap` / `ef_tensor_copy_to` (`map.rs`), and `ef_tensor_last_error_message` (`last_error.rs`). There is deliberately no other way to reach a tensor's bytes or extend its life from C, and — unlike when these were first added — none of the five distinguishes a handle by which library minted it; see the free-routing section above for why that distinction no longer exists to make.

**The model.** A tensor's lifetime is a plain atomic refcount (`EfTensorImpl::refs`): `into_handle` starts it at 1, `ef_tensor_retain` adds one with `Ordering::Relaxed`, and `release_own` (`ef_tensor_free`'s only implementation) subtracts one with `Ordering::Release` and, on the last release, an `Ordering::Acquire` fence before the `Box` is actually dropped — the standard pair for "the drop must observe every write that happened before every earlier release". CPU access is a scoped window, not a permanent property of the handle: `ef_tensor_map` takes `edgefirst_tensor::TensorDyn::map_bytes`'s `HostView` guard and stores it in `EfTensorImpl::map_state` (a `Mutex<Option<MapState>>`, so only one map may be outstanding per tensor at a time — a second call before the matching unmap is `EBUSY`); `ef_tensor_unmap` takes the guard back out of the mutex and drops it, and the guard's own `Drop` is the platform sync bracket — mmap stays resident, but IOSurface/dma-buf run their unlock/sync-for-device there. `ef_tensor_copy_to` never touches `map_state` at all: it takes its own short-lived read guard, copies, and drops the guard before returning, so it needs no outstanding map and leaves none behind — see `copy_to_coexists_with_an_outstanding_stored_map` in `map.rs` for the empirical proof that a local read guard and an outstanding stored map coexist freely on the `Mem` backend today.

**The no-unbracketed-view rationale ([r4]).** HAL's C surface exposes no unbracketed pixel view: `ef_tensor_plane_at` returns geometry and a shareable handle (offset, stride, size, fd/IOSurface id), never a CPU pointer. Every route to raw bytes goes through a bracket — `ef_tensor_map`/`_unmap`, or `ef_tensor_copy_to`'s self-contained one — so the sync bracket is structurally guaranteed to run before those bytes are declared valid or before the tensor is handed back to the platform. A caller cannot obtain a live pointer and skip the corresponding sync call, because there is no entry point that would hand one out.

**The EACCES write-gate.** `ef_tensor_map` refuses a *writable* request (`ReadWrite` or `Write`) against a tensor whose declared `CpuAccess` is not writable, at the C boundary, before ever reaching the backend — `EACCES`. This is narrow and one-directional: a *read* request against a not-writable declaration is not refused here at all; that mismatch is `edgefirst-tensor`'s own warn-and-allow territory (`note_unplanned_cpu_access`, best-effort telemetry on most backends, not an error). Backend-level mapping refusals — e.g. AHardwareBuffer's lock exclusivity — also surface as `EACCES` through the same `errno_for` translation, so the one errno covers both "the C boundary refused it" and "the backend refused it" without the caller needing to tell which.

**`TensorDyn::cpu_access()`.** The declared-access read-back the write-gate above needs is `edgefirst-tensor/src/tensor_dyn.rs`'s `TensorDyn::cpu_access() -> CpuAccess` (mirroring the pre-existing inherent method on the concrete backend types), which lets `map.rs` ask "does this tensor's declaration permit writes" without downcasting out of the dynamic wrapper.

**`map_bytes` returns a genuinely `'static` `HostView` — no transmute.** `MapState` in `map.rs` holds an `edgefirst_tensor::view::HostView<'static, u8>` even though the guard is produced from a `&TensorDyn` borrow with a much shorter lifetime in the caller's hand. This is not a lifetime-erasing transmute: `TensorDyn::map_bytes` shares ownership through the pin's keepalive `Arc` rather than borrowing the tensor, so the `'static` bound is honestly earned, not asserted past the compiler. `host_view_static_u8_is_send` in `map.rs` is a compile-time proof (not a runtime assertion) that every field of `HostView<'static, u8>` is independently `Send`, so `MapState` and `Mutex<Option<MapState>>` are automatically `Send` with no `unsafe impl` needed — the test exists so a future field addition that breaks the auto-derive fails to *compile* rather than passing silently.

**The frozen `ef_tensor_view` rule.** `EfTensorView { ptr, len }` is by-value and frozen forever: no version field, no reserved tail. Its size is baked into every consumer's call site the moment they compile against it, so it cannot evolve in place — a future need (say, a stride-aware view) is served by a *new*, suffixed type (`ef_tensor_view2`) and new entry points, never by growing this one. `tensor_view_is_two_pointers_wide_and_frozen` in `tensor-abi` pins its size (16 bytes) and alignment (8) as a layout golden, and `crates/tensor-capi/tests/c/test_layout_goldens.c` pins the same shape from the C side.

**Last-error and panic-hook conventions.** `ef_tensor_last_error_message` follows the `dlerror` convention: the errno return of a call stays the contract a caller programs against, and the message is advisory-only, thread-local, valid on the calling thread until that thread's next failing `tensor-capi` call. Only the map/refcount entry points above record a message on failure; retrofitting the rest of the surface is out of scope and left to a future pass. Every shielded entry point installs a process-global panic hook lazily — on the first shielded catch anywhere, via `std::sync::Once`, never at library load — that captures the panic payload into the last-error slot instead of letting Rust's default hook print a backtrace-shaped message to whatever process embeds this library; the hook still chains to the previous one when `EF_PANIC_VERBOSE=1` is set, checked per-panic rather than cached at install time.

**Field order and drop order.** `EfTensorImpl`'s `map_state` is its first field, directly followed by `inner`. Unlike a genuinely self-referential struct, this ordering carries no soundness requirement — `map_state`'s `HostView<'static, _>` borrows nothing from `inner`, per the keepalive-`Arc` point above — so Rust's own drop order (declaration order) is a convenience, not a requirement. `release_own` does not rely on that ordering either: at the last reference, it explicitly drains `map_state` (with a `log::warn!` if a map was still outstanding — a caller bug, `ef_tensor_map` without a matching `ef_tensor_unmap`, surfaced loudly rather than silently leaking the mapping guard inside the freed `Box`) *before* dropping the `Box`, so the platform sync bracket is guaranteed to run even on a caller's mistake.

**The `cpp_compat` knob.** `cbindgen.toml` sets `cpp_compat = true`, which is what makes the generated `#if defined(__cplusplus) || __STDC_VERSION__ >= 202311L` guards around `ef_dtype`/`ef_storage_kind`/`ef_cpu_access` correct under C++: without it, cbindgen's C23-fixed-underlying-type check tests only `__STDC_VERSION__`, which a C++ compiler's preprocessor treats as unset, so the fallback `typedef uint32_t ef_dtype;` would run and collide with the enum tag `ef_dtype` — already a type name in C++ on its own. `the_header_compiles_as_cpp17` in `src/lib.rs` is the executable proof this stays true: it toolchain-probes for a working `-std=c++17` compiler, verifies the probe itself can fail (a C++17-hostile construct must be rejected, or the gate proves nothing), and then compiles the real header under the same flags.

## Testing notes that are easy to get wrong

**Artifact freshness.** Neither `cargo test` nor `cargo test --all-targets` builds `staticlib`/`cdylib` targets — only `cargo build` does. A test that reads the built library therefore validates whatever was built *last*, which is how the "no accessor is exported" check was found to be passing against a previous build. Tests here check the artifact against `src/` mtimes and skip loudly by default; set `EF_REQUIRE_FRESH_ARTIFACTS=1` (CI, the Makefile's C target) to make staleness a hard failure.

**A skip must not be able to hide a defect.** The C tests probe the toolchain with a trivial translation unit *first*. Without that split, a genuine link failure — a symbol we removed, a broken export — is indistinguishable from "this host has no compiler" and gets swallowed as a skip. Dropping `#[no_mangle]` from `ef_tensor_free` left the C test passing until the probe was added.

**Generated headers are stale by default.** cbindgen regenerates on `rerun-if-changed=src/`; deleting or editing the header does *not* regenerate it. Any test reading `tensor.h` is meaningful only because a source change triggers regeneration.

## Workspace mechanics

This crate and its four `-capi` siblings live outside the root workspace's `members` set — the root `Cargo.toml`'s `exclude` list names them explicitly, with a comment explaining why. The reason is the static/dynamic feature switch: cargo unifies features across every package built in one invocation, so a workspace member could not let one consumer request `static` while another requests `dynamic` in the same `cargo build`. Excluding the five leaves and building each with its own `--manifest-path` sidesteps that unification entirely — every leaf resolves its own feature set. The cost is that neither `cargo build --workspace` nor `cargo test --workspace` touches these crates at all; they are two separate worlds, each built and tested through its own invocation, and the Makefile's `CAPI_MODULAR_CRATES` loop is what stitches the two worlds into one gate.

**`--target-dir target` is not optional.** Every one of those per-leaf invocations passes `--target-dir target`, pointing at the same directory `cargo build --workspace` already uses. Left at its default, an excluded package would build into its own `crates/<leaf>/target`, and this crate's artifact-freshness tests — the ones described above, which read the built `cdylib`/`staticlib` off disk and compare mtimes against `src/` — assume a single shared artifact directory. Two directories would mean the test could read a stale artifact from one location while the source it is checking lives in the other, silently defeating the freshness check rather than failing loudly.

**`EF_REQUIRE_FRESH_ARTIFACTS=1` is enforced, not advisory.** The Makefile's `test-capi-modular` lane and the CI job that mirrors it both set this variable, which turns "the artifact might be stale" from a loud skip into a hard failure. Without it, a test reading a leftover build from a previous invocation would pass for the wrong reason — the exact failure mode the freshness tests exist to catch, just moved one level up to the lane that runs them.

**Per-leaf lockfiles are release pinning, not drift.** Each of the five leaves carries its own `Cargo.lock`, reconciled to (not independently resolved from) the workspace's own dependency resolutions. A leaf's lockfile pins what that leaf ships as a standalone release artifact; it is not meant to track the root workspace lockfile automatically, and the two are expected to diverge over time as the root workspace picks up updates a given leaf's next release has not yet absorbed.

**Coverage has a conscious gap here.** `make test-rust`'s `cargo-llvm-cov` run only instruments what `cargo test --workspace` builds, and the five leaves are outside that invocation. Their tests run via plain `cargo test --manifest-path ... --target-dir target`, which exercises the code but contributes no lines to the coverage report. This is a deliberate trade-off rather than an oversight: instrumenting five additional per-invocation lanes for coverage would mean five more llvm-cov profiles to merge, for crates that are thin C surface over an already-covered implementation. The gap is recorded here so a future coverage regression investigation does not mistake it for something that broke.
